# 항목별 구현과 독립 검토

수정이 요청된 경우에만 이 절차를 적용한다. 메인 에이전트는 범위·소유권·판정·
통합 실행을 조율하고, 항목별 구현과 독립 검토를 서로 다른 에이전트에 맡긴다.

## 역할과 실행 설정

사용자·프로젝트 지침의 현재 `implementer`·`reviewer` 역할 설정을 사용한다.
스킬에서 구체 모델·effort를 별도로 고정하지 않는다. 사용자의 명시적 모델 지정과
예산·런타임 제한이 우선한다.

| 역할 | 책임 |
| --- | --- |
| 구현자 (`implementer`) | 배정된 항목의 최소 코드 변경과 필요한 행동 검증 준비 |
| 독립 검증자 (`reviewer`) | 완성된 변경의 계약·호출 경로·실패 반례를 읽기 전용으로 확인 |
| 메인 | 지적의 채택·거부, 파일 소유권, 통합 및 실행 증거, 최종 보고 |

실행 시 실제 모델·effort 지원 목록을 확인하고 없는 문자열을 전달하지 않는다.
명시적으로 지정한 모델을 사용할 수 없으면 임의 대체하지 않고 사용자가 허용한
대체 범위를 따른다. 같은 에이전트의 자기 검토를 독립 검증으로 표시하지 않는다.
가능한 작업은 진행하되 수행할 수 없는 단계와 영향은 알린다.

위임 호출의 실제 모델·effort, 검토자, 항목 범위와 반환 판정을 함께 기록한다.
에이전트가 답변에서 자칭한 모델을 실행 설정의 증거로 삼지 않는다. 이전 응답의
설정이 빠져 있으면 확인 가능한 호출 기록을 먼저 대조한다. 내용을 참고할 수는
있지만 설정이 확인되지 않은 응답을 지정 모델의 독립 검토 완료로 세지 않는다.

## 1. 구현 책임을 배정한다

각 구현자에게 다음을 전달한다.

- 항목 ID, 사용자 동작·실패 조건·원래 계약, 관련 소스와 감사 근거.
- 담당 파일·모듈과 편집 허용 범위, 다른 구현자가 소유한 파일.
- 보존할 기존 동작, 개인정보·평가·원격 반영 등 해당 작업의 제한.
- 관련 시나리오 ID·기대값 근거·관찰할 수용 결과, 적절한 검증 방법, 완료·중단 조건.
- 반환할 변경 요약, 실제 실행 명령·결과, 미실행 조건과 남은 위험.

다른 에이전트도 같은 작업 공간을 사용하므로 타인의 변경을 되돌리지 말고 현재
변경을 수용해 작업하도록 명시한다. 같은 파일의 편집은 순서대로 배정한다.
독립된 모듈만 병렬 처리하며, 항목마다 에이전트를 무조건 새로 만들지는 않는다.
서로 겹치는 후속 수정은 기존 구현자에게 맡길 수 있다. 에이전트의 재위임은 기본적으로
허용하지 않는다. 메인은 완료 전 중간 파일을 읽거나 같은 구현을 병행하지 않는다.

## 2. 완성된 변경을 독립적으로 검토한다

구현 완료 응답을 받은 뒤 별도 검증자에게 현재 소스·변경 범위·수용 조건을 전달한다.
최초 독립 검토는 구현자의 결론을 정답으로 주지 않는다. 관련 계약과 실행 근거는
제공하되 검증자가 원본 호출 경로와 변경을 직접 읽도록 한다. 불필요한 대화 전체나
허용되지 않은 원문 자료를 전달하지 않는다.

검증자는 다음을 확인한다.

- 실제 실패 조건이 해결되는지, 정상 입력·오류·취소·중복 요청의 계약이 유지되는지.
- 저장 성공과 화면 상태, 개인정보 수명, 실제 I/O 종료 등 해당 항목의 중요한 경계.
- 새 테스트가 제품 동작을 검증하는지, 단언이 구현을 그대로 복제하거나 항상
  성공할 수 있는지, 변경과 무관한 구조 확장이 생겼는지.
- 시나리오에 변경 영향이 있는 정상 흐름이 포함되는지, 기대값 근거와 판정 조건에
  빈틈이 없는지. 필요한 결과의 존재·내용을 확인하고 빈 값·출력 누락이 통과하지
  않는지와 위험에 맞는 최소 반례의 탈락 증거를 확인한다.
- 코드에서 확인한 사실과 실행으로 확인한 사실이 구분되는지.

결과는 `ACCEPT`, `REWORK`, `UNVERIFIED` 중 하나와 함께 반환한다. `REWORK`에는
파일·함수, 구체적 입력 또는 실행 순서, 예상·현재 결과, 보호해야 할 계약을 요구한다.
검토 범위에서 반례를 찾지 못했다는 사실을 결함 부재의 보증으로 표현하지 않는다.
검증자는 코드를 직접 고치거나 공용 빌드·기기를 동시에 사용하지 않는다.

## 3. 메인이 지적을 판정하고 반복한다

| 지적의 성격 | 메인의 처리 |
| --- | --- |
| 실제 실패 경로나 회귀가 확인됨 | 같은 구현자에게 근거를 돌려보내 수정하고, 같은 검증자가 변경과 인접 계약을 재검토한다. |
| 필수 근거가 없어 판정 불가 | 필요한 최소 소스·실행 증거를 보완한다. 근거 부족을 곧바로 제품 수정으로 바꾸지 않는다. |
| 취향·불필요한 해시 검사·무의미한 테스트·과도한 추상화 | 어떤 행동 오류를 잡지 못하는지 설명하고 거부하거나 최소 대안으로 좁힌다. |

SHA-256 자체를 금지하지 않는다. 실제 보안·아티팩트 무결성 계약을 검사하는 해시와,
로직 검증을 대신하는 형식적 해시 비교를 구분한다. 지적을 거부할 때도 타당한 부분은
남기고 수용·거부 이유를 기록한다. 비용이나 편의만으로 재현 가능한 결함을 무시하지 않는다.

`REWORK`의 사유가 모두 이 기준으로 거부됐다면 제품 코드나 테스트를 억지로 추가하지
않는다. 원래 verifier 판정은 보존하고, 메인의 최종 처리에 **메인 수용 — 비기능 요구
거부**와 근거를 별도로 기록할 수 있다. 필요하면 같은 verifier에 반증을 전달하되
`ACCEPT`라는 문구를 받기 위한 반복을 요구하지 않는다. 이를 독립 verifier의
`ACCEPT`로 바꿔 보고해서는 안 된다. 실제 반례나 필수 검증 공백이 남으면 이 처리로
완료를 대신할 수 없다.

새로운 근거가 나오면 반복하고, 같은 방식의 두 시도에서 판단에 필요한 새 근거가
없으면 방법을 바꾸거나 정확한 제약을 보고한다. 반복 횟수만으로 수용 기준을 낮추지
않는다. 권한·도구·예산 때문에 필수 단계를 수행할 수 없으면 그 단계는 미확인으로
남긴다. 긴 작업도 진행 조회를 반복하지 말고 완료·차단 알림을 기다린다.

## 4. 통합 후 영향을 다시 확인한다

같은 데이터나 호출 경계를 바꾼 후속 항목이 앞선 수정을 깨뜨릴 수 있으면 그 연결만
다시 검토한다. 기존 승인 코드와 시험에 영향이 없다면 전체 재검토를 반복하지 않는다.
공용 실행은 한 담당자에게 맡기며, 최종 결과가 남는 크기로 묶는다.
기존 실패와 변경 영향이 있는 기존 정상 시나리오를 다시 실행한다. 새 위험이
없으면 영향 없는 통과 검증은 반복하지 않는다.

런타임 실패가 나오면 제품 결함, 테스트의 잘못된 가정, 실행 환경 실패를 실제 증거로
구분한다. 수정한 제품 또는 테스트 변경은 그 범위에 맞게 독립 검토한 뒤 재실행한다.
시험 수를 늘리거나 단언을 약화해 실패를 없애지 않는다. 확인한 한계와 최종 실행
증거를 SKILL.md의 완료 보고 절차에 반영한다. 시나리오 실행 상태와 집계는
[시나리오 기록과 실행 판정](scenario-verification.md)을 따르며 코드 `ACCEPT`와
실행 `PASS`를 구분한다.

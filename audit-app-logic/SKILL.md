# 앱 로직 감사와 수정 검증

실제 사용자 동작에서 시작해 오류의 조건·영향·근거를 확인한다. 감사 결과, 코드 검토 판정, 실제 실행 결과를 구분해 전달한다.

## 요청 범위에 맞는 경로를 선택한다

| 사용자 요청 | 수행 범위 |
| --- | --- |
| 소스 검토, 문제 파악, 수정 전 검토, 수정 계획 | 조사와 필요한 보고·계획. 명시적 소스 검토 요청에서 앱 실행을 자동 시작하지 않는다. |
| 실제 동작 검증, 사용자 시나리오 실행, 고치지 말고 실제 검증 | 앱 코드·설정을 변경하지 않고 선정한 시나리오를 실행한다. 3단계 이후 4·5단계로 진행한다. |
| 감사하고 고치기, 발견 사항 개선, 승인된 항목 수정 | 감사 근거를 확정한 뒤 항목별 구현 → 독립 검토 → 필요한 실행 검증을 진행한다. |
| 앞서 완료한 감사의 후속 수정 | 기존 항목과 현재 소스를 대조하고 변경된 근거만 갱신한다. 전체 감사를 처음부터 반복하지 않는다. |

단순히 감사만 요청했다면 조사 경로를 선택하되, 실제 검증이 포함된 요청은 실행
경로로 진행한다. 발견 사항을 수정 권한으로 해석하지 않는다. 현재 대화에서 허용한
같은 범위의 수정과 비파괴 로컬 실행은 다시 승인받지 않는다. 원격·운영 데이터 접근,
원격 반영·배포·데이터 삭제나 새 비용 발생은 별도 권한 경계다. 확인이 필요한 선택이
있어도 독립적으로 진행할 수 있는 허용 작업은 계속한다.

## 1. 기준과 조사 범위를 고정한다

- 대상 앱·모듈, 주요 사용자 흐름, 완료 증거, 비목표와 실행 제한을 짧게 기록한다.
- 가까운 `AGENTS.md`와 README를 읽고 관련 정본 계약·ADR만 따라간다. 저장소가
  요구하는 탐색 도구가 있으면 우선 사용한다. 문서 전체를 한꺼번에 읽지 않는다.
- 현재 revision과 관련 미커밋 변경을 구분한다. 인계 문서와 과거 판정은 조사
  출발점이며 현재 결함의 증거는 아니다. 다른 작업의 변경은 보존한다.
- 허용 데이터·캡처·에이전트 전달 범위를 확인한다. 개인 데이터, 평가 정답,
  보호된 보관 영역을 편의를 위해 열거나 복제하지 않는다.
- 조사 경로에서는 빌드·UI 실행을 자동 시작하지 않는다. 실행 검증 경로에서는
  사용자 범위와 로컬 실행 정책에 맞는 최소 검증을 선택한다.
- 선정 범위의 사용자 시나리오 목록을 먼저 만든다. 작은 범위는 짧은 표로 충분하다.
  [시나리오 기록과 판정](references/scenario-verification.md)의 최소 정보·상태 정의를
  따르고, 조사로 확인한 호출 경로와 계약을 목록에 반영한다.

넓은 감사를 위임할 때만 저장·서비스, 화면 상태, 검색·백그라운드처럼 실제 책임
경계를 기준으로 나눈다. 최소 수의 읽기 전용 조사자를 사용하고 중첩 탐색을 피한다.
고정된 에이전트 수나 모든 디렉터리의 전수 열람을 요구하지 않는다.

## 2. 운영 호출 경로를 추적하고 반증한다

문제가 의심되는 함수만 보지 말고 다음 연결에서 필요한 부분을 확인한다.

`사용자 동작 → 입력·서비스 → 비동기 작업·저장 → 결과 소비자 → 화면·재조회`

분야별로 다음 질문 중 해당하는 것을 사용한다.

- **내용 보존:** 생성된 설명·키워드·날짜가 변환 과정에서 정렬·분할·유실되는가?
  표시용 값과 검색용 값이 다른데 한쪽 문제를 양쪽에 일반화하지 않았는가?
- **비동기 수명:** 중복 요청, 취소, 권한 변경, 응답 역전에서 최신 결과만 게시하는가?
  UI 취소와 실제 I/O 종료를 구분하는가? checkpoint와 실제 처리 집합이 일치하는가?
- **저장과 오류:** 빈 결과와 읽기 실패를 구분하는가? 성공 응답이 commit과 일치하는가?
  필수 후처리 실패 시 rollback·재조회·화면 상태가 같은 결과를 나타내는가?
- **화면 상태:** 실패 초안과 기존 목록을 보존하는가? 검색·기간·지도 범위·포커스가
  함께 전환되는가? 한 목록의 오류나 오래된 응답이 다른 상태를 덮지 않는가?
- **준비와 중단:** 필요한 자원이 준비된 뒤 동작을 허용하는가? 원인별 중단과
  사용자 취소를 보존하는가? 종료 시 접수된 저장·자원 정리를 기다리는가?

각 후보에 대해 정상 입력, 기존 guard, 상위·하위 호출자의 보완 동작, 실제 도달
가능성을 확인한다. 의도된 fail-closed 동작이나 아직 연결되지 않은 API를 곧바로
제품 결함으로 분류하지 않는다. 발생률·영향 데이터 수·모델 우위는 추정하지 않는다.

## 3. 발견 사항과 수정 계획을 만든다

발견 사항은 안정된 ID를 붙이고 관련 시나리오 ID와 아래 정보를 남긴다. 결함이 없는
정상 시나리오와 미구현 흐름도 시나리오 목록에 남긴다.

| 필드 | 필요한 내용 |
| --- | --- |
| 문제·영향 | 어느 사용자 동작에서 어떤 결과가 잘못되는지와 영향 범위 |
| 조건·계약 | 실패를 일으키는 입력·순서·오류 조건과 지켜야 할 동작 |
| 근거·반증 | 현재 파일·함수·행, 호출 연결, 확인한 보호 조건과 그 한계 |
| 확인 수준 | 소스로 확인 / 실행으로 재현 / 추가 확인 필요. 실행하지 않았으면 명시 |
| 수정 방향 | 최소 변경 위치, 보존할 계약, 기존 저장값·판본의 처리 여부 |
| 수용 조건 | 같은 실패 조건에서 관찰할 결과, 실패·취소·재시도·재실행 확인 범위 |

확인된 결함과 가설·제외 항목을 분리한다. 우선순위는 영향과 도달 조건으로 설명하라.
문서가 필요한 규모라면 저장소의 기존 작업 경로에 감사·계획·실행 기록을 둔다.

조사만 요청받았다면 5단계 기준으로 결과와 필요한 수정 계획을 보고한다. 변경 없는
실행 검증은 4단계로 진행한다. 수정이 요청된 경우에는
[항목별 구현·독립 검토](references/repair-loop.md)를 읽고 계속한다.

## 4. 실제 실행과 코드 판정을 구분한다

선정한 사용자 시나리오와 중요한 실패 경계를 기존 운영 UI 또는 실제 통합 경로로
검증한다. 기존 테스트를 먼저 활용하고, 단위 테스트를 기계적으로 늘리지 않는다.
필요한 장애 주입은 OS callback·I/O·외부 서비스 경계에 한정한다. 확인하려는 저장·
상태 전환·검색 로직을 성공을 반환하는 대역으로 바꾸지 않는다.

기대 결과의 존재·내용·최종 상태와 금지된 결과의 부재를 함께 확인하고, 완료 표시가
다음 동작의 기준이면 표시와 실제 후조건의 순서도 검증한다. 이전 또는
잘못된 결과가 없다는 사실만으로 성공 처리하지 않는다. 판정이 빈 값·출력 누락에도
통과할 위험이 있으면 최소 반례가 실제로 탈락하는지 확인한다. 구체적 기준은
[시나리오 기록과 판정](references/scenario-verification.md)을 따른다.

- 초기화 우회·별도 화면·테스트 전용 파이프라인의 성공을 정상 앱 E2E로 표현하지 않는다.
  기존 UI로 검증할 수 없는 조건은 별도 증거 수준과 미확인 범위로 남긴다.
- UI 실패는 실제 화면·접근성 요소·오류 상태로 제품 문제와 테스트 문제를 구분한다.
  캡처는 허용된 데이터·화면임을 확인한 범위에서만 한다. 대기 시간 증가나 단언
  삭제를 첫 대응으로 삼지 않는다.
- 테스트 코드의 객체 수명·트랜잭션·시간 정밀도 가정이 틀리면 원인을 기록한다.
  앱 코드·설정과 저장소의 기존 테스트 수정은 해당 변경 권한이 있는 범위에서만
  한다. 현재 허용 범위에서 만든 격리된 검증 스크립트는 검증 전용 경로에서도
  생성·보정할 수 있으며 별도 재승인을 요구하지 않는다. 잘못된 테스트를
  통과시키려고 제품 계약을 약화하지 않는다.
- 실행 자원을 공유하면 빌드·Simulator·기기를 한 담당자에게 맡겨 직렬 실행한다.
  로컬 정책의 고정 경로·디스크 검사·생성 및 정리 규칙을 따른다.
- 결과 파일·종료 코드·실제 시험 수를 확인한다. 중단되거나 최종 집계가 없는 로그는
  부분 증거다. 수정 후 기존 실패와 변경 영향이 있는 기존 정상 시나리오를 다시
  실행한다. 새 위험이 없으면 영향 없는 통과 검증을 반복하지 않는다. 실패 원인이
  미해결인데 재실행 한 번 성공했다고 해결로 닫지 않는다.

## 5. 완료 상태와 남은 한계를 보고한다

항목별 코드 검토 상태와 시나리오별 실행 상태를 따로 기록한다. `ACCEPT`는 코드
검토 판정이며 실행 `PASS`가 아니다. 실행 상태는 참조 문서의 `PASS`·`FAIL`·
`NOT_RUN`·`UNVERIFIED` 정의를 따른다. 실행 환경·준비 실패는 원인과 제한을
기록하고 제품 결함이나 통과로 세지 않는다.

최종 보고에는 수정한 항목, 실제 통과 범위, 주요 재작업, 미확인 조건과 근거 링크를
담는다. 선정 범위의 고유 시나리오 수를 분모로 통과·실패·미실행·확인불가 수를
보고하고, 실행 횟수와 재실행 수는 따로 밝힌다. 이를 전체 앱 커버리지로 표현하지
않는다. 합성 자료·호스트·Simulator 결과를 개인 데이터·모델 품질·
실기기·출시 게이트로 확대하지 않는다.

필요한 저장소 검사와 문서·색인 갱신, 사용한 자원 정리를 완료한다. 승인된 수정과
필요한 검증 또는 조사 보고가 끝나면 종료하고, 미검증 항목을 숨긴 채 전체 앱 검증
완료로 보고하지 않는다.

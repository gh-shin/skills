# 개발 작업에 적용하는 지침

요청 일부라도 개발 작업을 포함할 때 읽고 해당 부분에만 적용한다.
순수 조사나 문서 작업에 개발 절차를 추가하지 않는다.
개발의 목표·판정 기준은 공통 흐름에서 합의한 내용을 사용한다.

## 사실과 결과를 바꾸는 가정

가장 가까운 프로젝트 지침과 작업에 필요한 정본을 읽는다.
실제 코드, 호출 경로, 실행 상태에서 현재 동작을 확인한다.
문서의 설명이나 이름만으로 구현 상태를 단정하지 않는다.

공개 계약, 데이터의 의미·변경, 권한, 실행 환경에 관한 가정이 결과를 바꾸는지 확인한다.
사실로 확인할 수 있는 내용은 조사하고, 사용자 선택이 필요한 변경은 영향과 선택지를 반환한다.
범위 밖의 아키텍처나 계약 변경을 구현상의 편의로 결정하지 않는다.

## 구현 범위와 소유권

산출물과 관찰 가능한 동작을 중심으로 작업을 나눈다.
입력·의존성·완료 확인법과 함께 변경할 파일 또는 모듈의 소유권을 정한다.
결합도가 높으면 한 담당자가 맡고, 독립적인 범위만 허용된 역할에 위임한다.
현재 변경 상태에 맞춰 구현하며 다른 사람의 작업을 되돌리거나 덮어쓰지 않는다.
역할이나 파일 충돌이 결과에 영향을 주면 그 근거를 반환한다.

## 실제 동작 확인

합의 기준과 중요한 실패 경로를 실제 실행 또는 e2e 시나리오로 확인한다.
입력, 실행한 경로, 관찰한 결과, 충족한 기준을 연결한다.
명령 성공이나 빈 출력만으로 사용자 동작의 성공을 주장하지 않는다.
검증 결과는 검증한 산출물과 환경에만 적용한다.

불필요한 단위테스트와 구현을 복제한 테스트를 만들지 않는다.
검증이 필요하면 실제 동작과 판단에 중요한 실패 경계를 우선 확인한다.
변경·실패·미해결 위험이 있을 때만 검증을 넓히거나 반복한다.
실행할 수 없는 검증은 이유와 남은 확인을 보고하고 완료 근거로 쓰지 않는다.

## 전문 절차와 권한

작업에 맞는 사용 가능한 전문 스킬, 운영 담당자, 프로젝트 로컬 절차를 활용한다.
적용되는 운영 위임이나 환경 사용 규칙이 있으면 따른다.
특정 모델, 도구 스택, 운영 환경을 이 스킬의 필수 조건으로 고정하지 않는다.
외부 게시·배포·데이터 변경은 기존 권한 경계 안에서 수행한다.
구현 완료나 검증 통과를 추가 외부 작업의 승인으로 간주하지 않는다.

# Workflow

사용자가 기대하는 결과에서 출발해, 같은 뜻으로 목표를 이해하고 실제 근거로 완료를 판단한다.
조사, 기획, 문서, 분석, 제작, 개발 등 작업의 종류에 맞게 필요한 절차만 적용한다.
사용자 지시와 기존 범위·권한을 존중한다. 이 스킬은 추가 실행 권한을 부여하지 않는다.

## 적용 범위와 참조 선택

- 목표나 핵심 용어가 모호하거나, 여러 결정·의존성·실패 영향이 얽힌 작업에 적용한다.
- 진행 중인 작업에서는 기존 합의를 재사용하고, 새 근거나 상태 차이가 있는 부분만 다시 확인한다.
- 명확한 단일 작업은 짧은 목표 확인, 실행, 결과 확인으로 끝낼 수 있다.
- 인터뷰 산출물을 작성하거나 합의를 갱신할 때는 [references/interview-output.md](references/interview-output.md)를 읽는다.
- 요청의 일부라도 개발 작업을 포함하면 [references/development.md](references/development.md)를 읽고 해당 부분에만 적용한다.
- 지속 작업의 인계·재개, 기록 충돌, 외부 결과가 불확실한 실행의 복구를 다룰 때만 [references/recovery-and-resume.md](references/recovery-and-resume.md)를 읽는다.
- 순수 조사나 문서 작업에 개발 절차를 추가하지 않는다.
- 다른 스킬이나 도구를 설치하는 것을 이 흐름의 시작 조건으로 삼지 않는다.

## 1. 현재 목표와 상태를 확인한다

새 작업이면 사용자의 요청에서 기대 결과, 범위, 제약, 기존 결정을 추린다.
재개 작업이면 기존 기록을 실제 산출물·현재 상태·검증 근거와 대조한다.
과거 체크 표시만으로 완료를 단정하거나 외부 작업을 중복 실행하지 않는다.

다음 항목은 내부 점검에 쓰고, 사용자 확인은 2절의 순차 인터뷰 방식으로 진행한다.

- 사용자가 얻으려는 결과는 무엇이며, 왜 필요한가?
- 이미 합의한 내용과 현재 확인된 사실은 무엇인가?
- 결과나 다음 결정을 바꿀 미해결 사항은 무엇인가?
- 지금 승인된 범위에서 독립적으로 진행할 수 있는 일은 무엇인가?

기록이 없다는 이유만으로 전체 인터뷰를 반복하지 않는다.
사용자가 이미 답한 질문과 주어진 근거를 먼저 사용한다.

## 2. 인터뷰로 발견하고 의미를 맞춘다

인터뷰는 질문 목록을 채우는 절차가 아니다.
사용자도 놓쳤을 수 있는 검토 항목과 정의를 발견하고, 함께 판단할 수 있도록 설명한다.
예상 결과에서 거슬러 주요 단계, 의존성, 장애물, 결정점을 찾는다.
사용자에게 완성된 논리를 만들어 오도록 요구하지 않는다.

새 검토 항목을 제시할 때는 다음을 연결한다.

- 항목의 중요도, 지금 확인해야 하는 이유와 목표에 미치는 영향
- 가능한 선택지와 중요한 장단점
- 권장안이 있다면 그 근거와 남은 불확실성
- 선택을 아이디어나 계획에 반영할 위치

목표와 무관한 기능이나 산출물을 확장하지 않는다.
자료나 실제 상태로 확인할 사실은 직접 조사하고, 사용자 판단이 필요한 선택과 구분한다.
학술 근거나 최신 제품 사양·동작을 조사할 때는 질문에 맞는 일차 자료·공식 원문을 우선한다.
적용 버전·시점과 각 자료가 직접 뒷받침하는 주장을 구분한다. 검색 요약이나 다른 모델의 답변을 확인 근거로 대신하지 않는다.
자료가 필요하지 않은 작업에 웹 조사나 자료 체크리스트를 추가하지 않는다.
인터뷰 전체의 질문 수를 고정하거나 모든 불확실성을 없애려 하지 않는다.
결과·범위·비용·권한 등을 바꾸는 의미 있는 미결정만 사용자에게 확인한다.

### 한 번에 하나씩 질문하고 확인한다

한 번의 응답에는 하나의 결정에 관한 질문과 그 질문에서 확인할 정의 하나만 제시한다.
현재 판단에 필요한 용어 또는 기준의 뜻을 짧게 설명하고, 같은 판단을 돕는 사례·선택지·권장안을 붙일 수 있다.
한 문장이나 번호 하나에 별도로 답해야 하는 여러 질문·정의를 묶지 않는다.

사용자 답변을 기다린 뒤, 답변에서 확인된 뜻과 결정을 관련 목표·계획·체크리스트에 반영한다.
뜻이 불명확하거나 기존 합의와 충돌하면 같은 항목을 명확히 하는 질문 하나로 이어간다.
뜻이 확인되면 이미 받은 답은 재사용하고, 선행 결정이 해결된 항목 중 다음 판단에 가장 중요한 하나를 고른다.
사용자가 여러 항목을 한꺼번에 답해도 모두 반영한 뒤 남은 질문은 하나씩 제시한다.

다른 질문 후보는 내부에 남기고, 답변을 받기 전에 다음 질문을 추가하지 않는다.
질문 도구를 사용할 때도 한 번에 질문 하나만 전달하며, 답변을 기다리는 질문을 여러 개 만들지 않는다.

### 핵심 용어를 사례로 확인한다

목적, 방법, 단계의 같은 단어를 사용자와 에이전트가 같은 의미로 쓰는지 확인한다.
판단을 바꾸는 용어는 정의, 해당 사례, 반례 또는 경계 사례로 설명한다.
서로 같은 사례를 같은 상태로 판정하는지 확인한다.
익숙한 단어라는 이유로 합의를 추정하지 않는다.

특히 성공과 실패는 다음 층위를 구분한다.

- 프로젝트: 사용자가 기대한 최종 결과와 필수 기준을 충족하는가?
- 단계: 다음 단계에 필요한 산출물이나 결정 근거를 확보했는가?
- 시도: 정한 가설·방법으로 어떤 결과나 학습 증거를 얻었는가?

시도가 실패해도, 미리 합의한 학습 증거를 얻어 다음 결정을 바꾸면 허용된 진전일 수 있다.
시도의 결과와 단계·프로젝트의 판정은 각각의 합의 기준에 따라 기록한다.
학습이나 가설 기각이 목적이었던 단계는 그 기준을 충족하면 완료할 수 있다.
그 근거가 최종 결과의 기준까지 충족하는지는 별도로 확인한다.
실패 후 성공 기준을 임의로 재정의하거나 무익한 반복을 학습으로 합리화하지 않는다.

### 인터뷰의 종료 조건

다음 상태가 되면 인터뷰를 마치고 합의한 범위에서 실행한다.

- 기대 결과, 핵심 용어, 사례 판정에 대한 이해가 일치한다.
- 중요한 경로와 장애물을 함께 이해한다.
- 결과를 바꾸는 미결정이 해소되었거나, 조사 방법과 결정 시점이 정해져 있다.
- 성공·실패 기준과 확인 근거를 구분할 수 있다.

침묵을 합의로 간주하지 않는다.
중요한 미결정에 의존하는 실행은 기다리되, 독립적으로 승인된 작업과 조사는 계속한다.
인터뷰 결과에는 합의·결정과 실행·검증을 구분한 체크리스트를 포함한다.
작은 작업은 대화 안에 짧게 기록하고, 지속이나 인계가 필요할 때만 별도 기록을 만든다.

## 3. 필요한 수준으로 작업을 분해한다

관리 수준은 불확실성, 결합도, 의존성, 실패 영향, 되돌리기 가능성, 검증 난도와 조정 비용으로 정한다.
파일 수나 예상 시간만으로 복잡도를 판정하거나 고정 등급을 붙이지 않는다.
합의된 결과를 확인하는 데 충분한 최소 관리 수준을 선택한다.

불확실성을 줄이는 조사와 결과물을 만드는 실행을 구분한다.
조사 결과가 다음 선택을 바꾸면 조사부터 배치하고, 독립적인 실행은 병행할 수 있다.
활동 이름만 나열하지 말고 관찰 가능한 산출물과 목표 기여를 중심으로 나눈다.

각 하위 작업에는 필요한 만큼 다음 내용을 남긴다.

- 목표에 대한 기여와 관찰 가능한 산출물
- 작업 범위와 책임 또는 변경 소유권
- 필요한 입력, 의존성, 먼저 내려야 할 결정
- 완료 확인 방법과 중요한 실패 상황
- 중단 조건과 판단을 반환할 시점

큰 작업도 결합도가 높으면 한 담당자가 맡을 수 있다.
독립적인 작업을 나눌 이익이 있을 때만 현재 허용된 역할과 범위 안에서 위임한다.
위임은 권한이나 범위를 넓히는 수단이 아니다.
기존 기록과 담당자를 활용하고 중복 실행을 피한다.

## 4. 실행하고 근거에 따라 접근을 전환한다

합의한 목표·범위·제약 안에서 방법과 작업 순서는 자율적으로 조정한다.
결과의 의미, 성공 기준, 주요 비용, 범위 또는 권한이 달라지면 해당 부분을 사용자와 다시 합의한다.
새 결정을 관련 목표, 계획, 체크리스트에 함께 반영한다.

외부 효과가 있는 실행은 중복 방지 방법과 결과 확인 근거를 정한다.
timeout이나 응답 유실은 실패 확정이 아니다. 결과가 불확실하면 재시도 전에 실제 외부 상태와 실행 영수증 등 직접 근거를 대조한다.
기록과 실제 상태가 충돌하거나 결과를 확인할 수 없으면 영향을 받는 새 변경만 보류하고 읽기 전용 확인과 복구부터 진행한다.
독립적으로 승인된 작업은 계속할 수 있다. 복구·보상도 위험과 기존 권한 범위 안에서 진행하며, 유효한 기존 승인을 재사용한다.

다음은 진행 방식의 재검토 신호다.

- 같은 실패가 새 근거 없이 반복된다.
- 중요한 전제가 무너지거나 상충하는 증거가 나온다.
- 실제 경로가 예상 경로와 크게 달라진다.
- 계속 진행해도 목표 판단에 필요한 증거를 얻지 못한다.

재검토 시 원인 가설과 그 가설을 구분할 관찰 또는 실험을 정한다.
관찰로 원인을 구분한 뒤 필요한 지점으로 돌아가고, 전환 이유를 재개 가능한 수준으로 남긴다.

| 관찰한 원인 | 돌아갈 지점과 다음 판단 |
| --- | --- |
| 일시적인 도구 오류 | 안전한 재시도 가능 여부 확인. 외부 결과가 불확실하면 재시도하지 않고 상태부터 대조 |
| 정보 부족 | 다음 결정을 바꿀 정보를 조사 |
| 전제 또는 목표 해석의 불일치 | 조사·계획을 갱신하거나 해당 의미를 재합의 |
| 결과물 결함 | 영향 받는 결과물을 수정 |
| 서로의 입력·출력 불일치 | 통합 상태와 계약을 확인 |
| 측정·검증 수단의 문제 | 검증 설계를 보완 |
| 상태 충돌 | 해당 변경을 보류하고 실제 상태 대조·복구 |
| 예산·권한의 한계 | 해당 사용자 결정이 필요하면 확인하고, 한계에 걸린 작업은 중단 |

실패마다 처음부터 다시 시작하거나 전체 작업을 중단하지 않는다.
이미 정해진 정책·예산·재시도 한도를 따른다. 별도 횟수나 모든 작업의 예산 인터뷰를 추가하지 않는다.

## 5. 과정과 산출물을 검토한다

과정의 견고함은 목표와 판정의 일관성, 결정·전환 근거, 재개 가능성으로 확인한다.
산출물의 견고함은 합의 기준과 중요한 실패 상황의 실제 확인 결과로 판단한다.
활동량, 자신감, 오래된 검증 결과를 현재 산출물의 완료 근거로 대신하지 않는다.

검토 결과는 다음처럼 구분한다.

- 완료를 막는 결함: 필수 기준 미충족, 중요한 실패 상황 미해결, 이번 작업이 만든 회귀 또는 승인 범위 밖 변경
- 선택 개선: 완료 기준은 충족하지만 추가 이익을 얻을 수 있음
- 별도 항목: 현재 합의와 관계없고 이번 작업이 만들거나 건드리지 않은 기존 문제, 또는 추가 제안

기존 문제라도 목표의 필수 조건을 막으면 완료 판단에 반영하고 필요한 범위 결정을 확인한다.
관련 수정·복구에서는 다른 작업자의 변경을 보존한다.

새 근거가 목표 자체의 타당성을 무너뜨리면 분류만 하고 넘기지 말고 그 영향을 명시한다.
영향이나 불확실성이 크고 독립적인 판단이 유익할 때는 허용된 독립 검토를 활용한다.
모든 작업에 별도 리뷰를 의무화하지 않는다.

## 6. 상태를 남기고 종료한다

기존 작업 기록을 우선 사용한다. 특정 상태 폴더나 별도 파일을 강제하지 않는다.
지속·인계가 필요하면 목표, 핵심 용어, 체크 상태, 판단 근거, 다음 행동과 막힘을 최소한으로 남긴다.
중요한 산출물 변경, 검증 완료, 막힘 확정, 중요한 전제·결정 변경, 외부 결과 확인 시점과 인계·중단 전에 기존 기록을 갱신한다.
실제 근거, 다음 행동, 반복하면 안 될 행동을 남긴다. 모든 읽기·검색·도구 호출마다 기록하지 않는다.
완료한 일, 미검증 항목, 남은 불확실성을 구분해 보고한다.
현재 산출물에 적용되는 증거를 연결하고, 미측정·미검증 상태는 그대로 표시한다.

필수 기준을 확인하고 완료를 막는 결함을 해결했으면 종료한다.
선택 개선 때문에 완료한 작업을 계속 재개하지 않는다.
목표를 달성할 수 없다는 근거가 생기면 충돌과 남은 선택을 설명하고 임의의 다른 목표로 바꾸지 않는다.

중요한 오류나 반복 실패에서는 관찰, 원인, 근거, 적용 범위를 개선 후보로 남긴다.
재사용 가치와 근거가 확인되면 회귀 검증·스킬·규칙 개선 후보로 연결하고, 후속 승인 작업에서 효과를 확인한다.
한 사례를 즉시 전역 규칙으로 바꾸거나 현재 권한 없이 설정·스킬을 자동 수정하지 않는다.
선택적인 학습이나 추가 효과 측정을 이미 끝난 작업의 새 완료 조건으로 삼지 않는다.

** 인터뷰의 의의 **
사용자 인터뷰의 목적은 두 가지다.

1. 사용자의 요청에 대해 자신도 몰랐던 검토항목이나 정의를 발견하여 그것을 어떻게 아이디어에 녹이고 구체화 할 것인가? 사용자의 요청은 대체로 모호하고 막연하여 완벽한 논리로 완성할 수 없다. 이것을 최대한 구체화하여 최종 목표가 중간에 흔들리거나, 목표까지 가는 단계에서 갑작스러운 결정사항이 튀어나오는 현상을 방지한다. 완성까지 도달하는데 까지의 여정과 장애물은 예상된 것이어야하며 초기부터 고려되어야한다. 작업이 완료되었을 때, 사용자가 이해할 수 없는 결과물이 나와선 안된다.

2. 용어 정의 확정: 해당 요청에서 성공의 의미는 무엇인가? 실패의 의미는 무엇인가? A는 실패로 볼 것인가? B는 실패지만 실질적인 성공의 과정으로서 의미를 가지고 있어 실패로 보지 않을것인가? 등, 목적과 방법, 그 목적까지 도달하는데 있는 여러가지 단계에서 등장하는 여러 용어들에 대해 유저와 에이전트가 공통의 이해도를 가지고 있어야한다. 유저는 에이전트가 아니고, 에이전트도 유저가 아니다. 이런 사소한 용어들에서 유저와 에이전트 사이에 오해가 발생하게 된다면, 사소한 오해가 누적되어 프로젝트 구현이 완전히 잘못되거나 무의미한 작업이 반복되어 최종목표와 관련없는 결과물이 나올 수 있다.
